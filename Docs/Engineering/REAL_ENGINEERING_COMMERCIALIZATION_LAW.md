# HooshyarOS Real Engineering & Commercialization Law

Status: **GOVERNING / FAIL-CLOSED**

This law replaces the assumption that successful code generation, unit tests, or a successful build implies a real product. It is the mandatory operating contract for autonomous construction and commercialization.

## 1. Truth hierarchy

Evidence has a strict order of authority:

1. **Observed runtime/application behavior** on the built product.
2. **Independent black-box acceptance** in a fresh execution environment.
3. **Integration behavior** across real boundaries and durable state.
4. **Focused behavioral tests** against the public contract.
5. **Static/source evidence**.
6. **Documentation or narrative claims**.

A weaker level may never promote a capability to a stronger level.

## 2. No self-certification

The component that proposes or implements a change MUST NOT be the sole authority that declares the change verified.

AI may:
- inspect;
- reason;
- propose;
- implement;
- repair;
- generate test candidates.

AI/autonomous construction MUST NOT treat its own generated assertions, mocks, screenshots, exit messages, or source markers as sufficient proof of real behavior.

The acceptance oracle MUST be deterministic, independently executable, and separated from the implementation contract. Changes to a production implementation and changes to its acceptance oracle MUST NOT be silently coupled in the same repair operation.

## 3. Real-product rule

A capability is **real** only when its claimed postcondition is observed after execution.

Examples:
- an installer is real only after installation on a clean machine/runner;
- a runtime is real only after it starts and serves the required endpoint;
- persistence is real only after write → process/database restart → readback;
- tenant isolation is real only after positive and negative cross-tenant tests;
- an execution workflow is real only after an independently observable side effect;
- uninstall is real only after the installation root, registration and shortcuts are actually gone.

A script printing `SUCCESS` is not evidence of success.

## 4. Fresh-environment rule

Commercial acceptance MUST run from the produced artifact in a fresh or isolated environment whenever the claim concerns installation, deployment, runtime lifecycle, persistence, security or user-facing behavior.

The build workspace itself is not sufficient evidence for installation or deployment claims.

## 5. Artifact provenance rule

Every commercial artifact MUST have:

- exact commit identity;
- artifact path/name;
- non-zero size;
- SHA-256 of the actual produced bytes;
- build command and exit code;
- execution timestamp;
- verification environment identity;
- acceptance result.

The verifier MUST compare the recorded hash/size with the actual artifact, not merely check that fields are present.

## 6. Evidence manifest rule

`Docs/Evidence/commercial-product-reality.json` is an **evidence record**, not a permission slip.

It is valid only when generated by an executed verification workflow and when every required claim is backed by an observed postcondition. Missing, stale, malformed, commit-mismatched, contradictory or manually asserted evidence MUST fail closed.

The manifest MUST identify its generator (`generatorId`), verification mode (`BLACK_BOX_RUNTIME` or equivalent), commit, environment and execution timestamp.

## 7. Completion-state law

The canonical state machine is:

`DOCUMENTED → IMPLEMENTED → BEHAVIORALLY_VERIFIED → INTEGRATION_VERIFIED → PRODUCTION_VERIFIED → COMMERCIAL_READY`

No state may be inferred from file existence. No state may be skipped. `COMMERCIAL_READY` requires all mandatory P0/P1 commercial gates and real application acceptance.

`productComplete=true` is forbidden while any mandatory reality gate is missing or blocked.

## 8. Repair law

A repair cycle is successful only if:

`failure observed → root cause identified → bounded repair → target postcondition observed → independent verification → checkpoint`

If the repair script does not change the intended target, changes an unintended target, fails its postcondition, or only emits a success message, the repair is **FAILED/BLOCKED**.

Automatic repair MUST NOT create implementation + test + commit + push merely to make the repository appear healthy.

## 9. Canonical-boundary law

Every capability has exactly one canonical owner and one canonical product artifact boundary.

The autonomous system MUST NOT create parallel implementations because the existing implementation is inconvenient. Duplicate roots, duplicate classes, duplicate productization builders and competing installers are release blockers until one path is explicitly canonicalized or deprecated.

## 10. Small-change law

Default construction unit:

**one capability → one coherent implementation → one focused behavioral test → one documentation update when required → one commit**.

Large-scale speculative generation is prohibited. Work must advance from the next evidence-backed gap, not from a request to generate an entire architecture.

## 11. Standard-tool law

Before inventing infrastructure, reuse a mature standard component when it satisfies the frozen architecture and security requirements.

Examples include PostgreSQL/SQLite as appropriate, Redis, FastAPI/standard HTTP frameworks, established queue systems, standard identity/RBAC providers, and established security scanners.

A hand-written replacement requires a recorded architectural reason.

## 12. Verification stack

Risk-proportional verification MUST combine independent layers where applicable:

- Type/static analysis;
- unit/property tests;
- integration tests;
- black-box application tests;
- adversarial/security tests;
- dependency vulnerability scanning;
- runtime health/readiness checks;
- artifact/install/upgrade/uninstall tests;
- persistence/restart/recovery tests;
- performance/load evidence;
- customer acceptance/proof-of-value evidence.

A green unit suite alone never authorizes commercial readiness.

## 13. Customer-data law

Customer data, models, formulas, methods, knowledge, evidence and derived intelligence remain tenant/customer scoped.

Cross-tenant access, cross-tenant learning, implicit privileged plaintext access and reuse of customer data without explicit authorization are forbidden. Security claims require positive and negative runtime evidence.

## 14. Domain/legal law

Iranian tax, accounting, privacy, regulatory and legal compliance MUST be grounded in authoritative current sources and, where legally consequential, qualified human review.

AI-generated interpretation is never the final legal authority.

## 15. Commercialization law

Commercialization proceeds in this order:

`REAL PRODUCT → SECURITY/ISOLATION → DURABLE DATA → PROOF OF VALUE → CONTROLLED TRIAL → CUSTOMER ACCEPTANCE → COMMERCIAL OFFER → PRODUCTION SCALE`

Default trial: 30 days. Extension to 60/90 days requires evidence-backed justification. Conversion requires measured customer value and acceptance.

## 16. Human responsibility boundary

The goal is **one human + AI/tooling**, not zero accountability.

Human approval remains mandatory for at least:
- final security acceptance before real customer data;
- legally consequential compliance claims;
- production credentials/external account activation;
- final commercial release approval.

All mechanical work that can be safely automated remains autonomous.

## 17. Failure behavior

When evidence is insufficient, contradictory or unavailable:

**BLOCK — PRESERVE EVIDENCE — REPORT EXACT GAP — CONTINUE SAFE WORK ONLY.**

Never convert uncertainty into `READY`.

## 18. Operational command policy

The autonomous builder may continue construction automatically, but every cycle must pass:

`AUDIT → DISCOVER → RISK → PRIORITIZE → PLAN → IMPLEMENT/REPAIR → FOCUSED VERIFY → INTEGRATE → REAL-RUN VERIFY → EVIDENCE AUDIT → CHECKPOINT → RE-EVALUATE`

Commercial productization is a separate gate after engineering verification; it is never implied by repository completeness.

## 19. Definition of done

The only acceptable completion statement is evidence-specific:

- **Built** — source implementation exists.
- **Verified** — behavior was executed and independently checked.
- **Production verified** — the deployed/runtime path passed its required production gates.
- **Commercial ready** — all mandatory product, security, persistence, operational, compliance and customer-value gates passed.

If a claim cannot be tied to an observed artifact/postcondition, it MUST NOT be reported as complete.
