# HooshyarOS Real Engineering & Commercialization Law

Status: **GOVERNING / FAIL-CLOSED**

This law is the mandatory operating contract for autonomous construction and commercialization. It replaces the assumption that successful code generation, unit tests, or a successful build implies a real product.

## Core laws

1. **Truth hierarchy:** observed runtime/black-box behavior outranks integration evidence, which outranks unit evidence, which outranks source/documentation. A weaker level can never promote a stronger completion state.
2. **No self-certification:** the implementation author/generator MUST NOT be the sole authority that declares its own change verified. Acceptance uses a deterministic independent oracle or black-box runtime observation.
3. **Real-product rule:** a capability is real only when its claimed postcondition is observed after execution. A `SUCCESS` message is not evidence.
4. **Fresh-environment rule:** installation, deployment, runtime lifecycle, persistence/restart, security isolation and user-facing acceptance are verified from the produced artifact in a fresh or isolated environment whenever practical.
5. **Artifact-provenance rule:** commercial artifacts require exact commit, actual SHA-256, actual non-zero size, build command/exit code, verification environment and observed acceptance result. The verifier compares the recorded hash/size with the actual bytes.
6. **Evidence-manifest rule:** `Docs/Evidence/commercial-product-reality.json` is an evidence record, not a permission slip. It must be generated by an executed verification workflow and must fail closed when missing, stale, malformed, contradictory or commit-mismatched.
7. **Repair-postcondition rule:** repair succeeds only after `failure observed → root cause → bounded repair → target postcondition observed → independent re-verification → checkpoint`.
8. **Canonical-boundary rule:** one capability has one canonical owner and one canonical product artifact boundary. Duplicate engines, builders, installers or parallel semantics are release blockers until explicitly deprecated/canonicalized.
9. **Small-change rule:** default construction unit is one capability → one coherent implementation → one focused behavioral test → one commit. Large speculative generation is prohibited.
10. **Standard-tool rule:** prefer mature standard infrastructure over hand-written substitutes; a replacement requires a recorded architecture/security reason.
11. **Verification-stack rule:** use risk-proportional static, unit/property, integration, black-box, security, dependency, runtime, persistence/recovery and acceptance verification as applicable. A green unit suite alone never authorizes commercial readiness.
12. **Customer-data rule:** customer data, models, formulas, methods, knowledge, evidence and derived intelligence remain tenant/customer scoped. Cross-tenant leakage is a release blocker.
13. **Domain-authority rule:** legally consequential Iranian tax/accounting/privacy/compliance claims require authoritative current sources and appropriate human approval. AI output is not the final legal authority.
14. **Commercialization order:** REAL PRODUCT → SECURITY/ISOLATION → DURABLE DATA → PROOF OF VALUE → CONTROLLED TRIAL → CUSTOMER ACCEPTANCE → COMMERCIAL OFFER → PRODUCTION SCALE.
15. **Human-accountability rule:** the goal is one human plus autonomous tooling, not zero accountability. Final security acceptance, legally consequential compliance, production credentials/external activation and final commercial release require explicit human approval.
16. **Fail-closed rule:** insufficient, contradictory or unavailable evidence means `BLOCK — PRESERVE EVIDENCE — REPORT EXACT GAP — CONTINUE SAFE WORK ONLY`.

## Operational cycle

`AUDIT → DISCOVER → RISK → PRIORITIZE → PLAN → IMPLEMENT/REPAIR → FOCUSED VERIFY → INTEGRATE → REAL-RUN VERIFY → EVIDENCE AUDIT → CHECKPOINT → RE-EVALUATE`

Commercial productization is a separate gate after engineering verification; repository completeness never implies commercial readiness.

## Completion semantics

- **Built:** source implementation exists.
- **Verified:** behavior was executed and independently checked.
- **Production verified:** the deployed/runtime path passed its required production gates.
- **Commercial ready:** mandatory product, security, persistence, operations, compliance and customer-value gates passed.

If a claim cannot be tied to an observed artifact/postcondition, it MUST NOT be reported as complete.
