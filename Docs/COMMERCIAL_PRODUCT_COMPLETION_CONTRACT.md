# Commercial Product Completion Contract

## Commercial completion layers

Every commercial capability must be evaluated across four levels:

1. **Unit evidence** — focused implementation test.
2. **Integration evidence** — interaction with owning engines/contracts.
3. **Application evidence** — runnable product path/UI/API/persistence behavior.
4. **Acceptance evidence** — end-to-end user-value path using representative data.

Only level 1 or 2 evidence must never be promoted to commercial completion.

### Machine-generated commercial reality manifest

The four evidence levels above are necessary but are not allowed to remain a narrative checklist. Before `productComplete=true`, the construction system MUST produce:

`Docs/Evidence/commercial-product-reality.json`

with `schemaVersion: 1`, `status: "VERIFIED"`, `generatorId: "HooshyarOS.RealityVerifier.v1"` and `verificationMode: "BLACK_BOX_RUNTIME"`.

The manifest MUST be generated by an executed verification process and MUST bind itself to the exact repository commit under test, a verification environment and an execution timestamp. The audit must reject missing, malformed, unverified or commit-mismatched evidence.

The manifest MUST contain successful command evidence (`exitCode: 0`) where every command also records an observed postcondition. A build exit code alone is never a runtime postcondition.

The manifest MUST contain evidence for:

- installer produced, with actual artifact path, SHA-256 and non-zero size;
- installation completed;
- product launched;
- health/readiness passed;
- dashboard/API endpoint responded successfully;
- desktop/browser lifecycle verified without losing the required runtime;
- uninstall completed and cleaned the installation;
- representative application/API/UI behavior executed;
- real persistence write and restart/readback succeeded;
- authentication/authorization and tenant isolation were exercised;
- audit/observability evidence was produced;
- representative end-to-end customer value path succeeded.

The verifier MUST compare the recorded artifact SHA-256 and size with the actual produced bytes. Merely populating these fields is invalid evidence.

A source file, a unit test, a mocked process, a build exit code, a screenshot, a generated success message, or a textual claim MUST NOT be substituted for executed application/acceptance evidence.

If an external dependency is genuinely unavailable, the manifest MUST record it as `required: true, status: "BLOCKED"` with its exact name. A required blocked dependency prevents `productComplete=true`.

### Anti-circular verification rule

The implementation author/generator MUST NOT be the sole authority that declares its own change verified. The acceptance oracle MUST be deterministic and independently executable. Changes to implementation and changes to the acceptance oracle are separate governance actions and must not be coupled merely to make a check pass.

## Completion states

The audit must report these states independently:

- `assistantComplete`
- `canonicalPlatformConstructionComplete`
- `commercialProductRuntimeComplete`
- `externalProductionDependenciesComplete`
- `productComplete`

`productComplete` may be `true` only when all required in-repository commercial layers are verified and no required external dependency is falsely treated as satisfied.

If a required external dependency is unavailable, report `BLOCKED_EXTERNAL_DEPENDENCY` with exact evidence and continue all safe repository-native work.

## Autonomous construction rule

The Python-first autonomous builder must treat this document as a **commercial completion audit contract**, not as permission to redesign the architecture.

For every audit cycle:

`READ GOVERNING SOURCES → AUDIT COMMERCIAL LAYERS → DISCOVER REAL GAP → SELECT ONE KNOT → CHECK OWNER/DEPENDENCIES → IMPLEMENT → FOCUSED TEST → INTEGRATION TEST → APPLICATION/ACCEPTANCE TEST → EVIDENCE AUDIT → COMMIT → PUSH → RE-AUDIT`
