--------------------------------------------------------------------
1. DISCOVERY (current-state scan)
--------------------------------------------------------------------
The canonical session owner already implements expired-session pruning:

  Backend/HBOS/Engines/UserManagementEngine.ts:391
    cleanupExpiredSessions(): number
      DELETE FROM sessions WHERE expires_at <= ?

and it is composed by the commercial identity service:

  Backend/HBOS/Product/CommercialIdentityService.ts:371
    cleanupExpiredSessions(): number

But the only callers in the whole repository are TESTS:

  git grep -n "cleanupExpiredSessions" -- "*.ts" "*.cjs"
    UserManagementEngine.ts:391          (definition)
    CommercialIdentityService.ts:371-372 (delegation)
    UserManagementEngine.test.ts:125     (only caller)

The commercial runtime never invokes it. Its request path only removes a session
row LAZILY, when that exact token is presented again:

  CommercialIdentityService.getSession()
    -> UserManagementEngine.getSessionRecord()   (SELECT, no expiry logic)
    -> if isExpired(record): deleteSession(...)  (only for a presented token)

Consequence: in a long-running commercial deployment every login/register/
passwordless-bootstrap row whose session expires and whose cookie is never
presented again stays in the `sessions` table forever. The table grows without
bound (unbounded disk growth, monotonically slower session lookups) even though
the canonical owner method that prevents exactly this exists and is unit-tested.

--------------------------------------------------------------------
2. REPRODUCTION (pre-fix behaviour)
--------------------------------------------------------------------
The new control test drives the runtime with `sessionSweepIntervalMs: 0` (no
sweep), lets the injected clock pass the 60 s session TTL, and reads the canonical
owner's `sessions` row non-destructively (`getSessionRecord()` applies no expiry
logic, so a present row proves it was never deleted):

  "leaves expired rows in place when the sweep is disabled" -> row still present

i.e. the pre-fix runtime is exactly the no-sweep path: expired rows accumulate.

--------------------------------------------------------------------
3. REPAIR (canonical owner, minimal)
--------------------------------------------------------------------
`Backend/HBOS/Autonomous/Runtime/CommercialRuntimeServer.ts`:
  - new option `sessionSweepIntervalMs` (default `DEFAULT_SESSION_SWEEP_INTERVAL_MS`
    = 5 minutes; `0` disables for explicit test control);
  - the runtime schedules `identity.cleanupExpiredSessions()` on that interval;
  - the timer is `unref()`'d so it can never hold the process open, and it is
    cleared by the existing `server.once("close", close)` handler so no handle
    leaks in tests (the F1/F2 flake class is explicitly avoided);
  - a sweep failure is swallowed so lifecycle maintenance can never take the
    runtime down.

No new engine, no second session store, no changed route/contract/criterion. No
persistence, security or completion-gate change.
