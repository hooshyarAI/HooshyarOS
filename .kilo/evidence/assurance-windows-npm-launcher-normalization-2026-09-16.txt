2. SELECTION BASIS
================================================================================
After the predecessor knot closed, the mandated continuation scan searched the
repository for the same defect class (a Windows `.cmd`/`.bat` launcher spawned with
`shell: false`, which Node rejects with EINVAL before the child starts). The scan
found the identical defect in three further canonical launchers:

| Owner | Entry point | Defect |
|---|---|---|
| scripts/real-product-qualification.cjs | npm `product:real:qualification` | spawnSync('npm.cmd', …, { shell: false }) |
| Backend/HBOS/Autonomous/Product/AutonomousProductFactory.ts | npm `product:factory:contract` | spawn('npm.cmd', …) and execFileSync('npm.cmd', …) × 2 |
| scripts/autonomous-ci-repair-runner.cjs | .github/workflows/autonomous-ci-repair.yml | exec helper spawnSync('npm.cmd', …, { shell: false }) |

One coherent root cause (Node cannot spawn `.cmd`/`.bat` without a shell) ⇒ one
bounded change set, in accordance with the queue rule "One coherent root cause = one
bounded change set = one test boundary = one commit". Each owner received the same
minimal normalization; no unrelated task was combined.

3. ROOT CAUSE (already proven by the predecessor knot, re-used)
================================================================================
  shell:false npm.cmd  -> status null  error EINVAL
  shell:true  npm      -> status 0     error undefined
  cmd.exe /d /s /c npm -> status 0     error undefined
No product/runtime behavior caused the failure; the launchers could not start the
npm CLI at all on Windows.

4. REPAIR (each owner minimal; repository-consistent convention)
================================================================================
Common convention: on Windows launch the npm CLI through
`process.env.ComSpec || 'cmd.exe'` with `/d /s /c "npm <args>"`; on POSIX spawn
`npm` directly. This is the same convention already used by
scripts/web-product-acceptance.cjs, scripts/security-tenant-acceptance.cjs,
scripts/autonomous-factory-loop.cjs, Backend/HBOS/Autonomous/Runtime/FinalProductFactoryRunner.ts,
LocalConstructionToolset.ts and KiloCodeExecutionAdapter.ts.

- scripts/real-product-qualification.cjs — extracted `launchNpm(args, stdio)` and
  `run(label, args)`; a failed launch now reports `exitCode`, `signal` and
  `launcherError` instead of silently collapsing into exit 1; `main()` is guarded by
  `require.main === module` and the helpers are exported for behavioral testing.
- Backend/HBOS/Autonomous/Product/AutonomousProductFactory.ts — new exported
  `npmInvocation(args)` resolver used for the two runtime launches, `npm test` and the
  `npm --version` prerequisite probe; new `stopChild()` terminates the whole process
  tree on Windows (`taskkill /PID <pid> /T /F`) instead of `child.kill()`, which would
  leave the npm/node runtime holding the port and database and could let the restart
  step observe a stale process instead of a real recovery.
- scripts/autonomous-ci-repair-runner.cjs — new `normalizeCommand(command, args)`
  helper routes only `.cmd`/`.bat` commands through the command processor and leaves
  native executables untouched; the load-time repair-context validation moved into
  `assertRepairContext()` called by `main()`, and `main()` is now guarded by
  `require.main === module`, so the module can be imported for testing without
  executing the CI repair loop.

No capability was reordered/added/removed, no criterion weakened, no completion flag
changed, and no engine/registry/lifecycle/architecture code touched.
