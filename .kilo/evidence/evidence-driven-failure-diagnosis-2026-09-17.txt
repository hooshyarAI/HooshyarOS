diagnosis contract:
  - FailureEvidence { output, issues?, capabilityId?, targetEngine?,
    dependencies?, changedFiles? }
  - FailureDiagnosis { traceId, type, primaryFile, evidencePresent, chain[],
    rootCauses[], blastRadius{ directFiles, owners, dependents, capabilities,
    bounded, scannedFiles } }
  - chain: ordered steps parsed from the real output shapes emitted by tsc
    (TS####), Jest (FAIL suite, assertion, timeout), module resolution
    (Cannot find module), the Windows launcher path (EINVAL / "is not
    recognized as an internal or external command"), and construction gate
    issues.
  - rootCauses: ranked candidates (HIGH/MEDIUM/LOW) with the evidence that
    produced them; empty when no failure signal exists.
  - blastRadius: direct files named by the evidence + direct importers found by
    a bounded reverse-import scan of Backend/ (DEFAULT_MAX_SCAN_FILES=4000,
    files >256 KiB skipped); bounded=true only when the scan completed under
    the cap.
  - traceId: canonical ProvenanceTrace.createTraceId() — reused identity, no
    parallel id scheme.
  - analyze(output) is retained for the existing heal orchestrator contract.
  - No architecture change, no new engine, no duplicate registry/store.

Integration (real consumer): AutonomousBuildDaemon now diagnoses a failed knot
on its failure path and records the diagnosis in the run history and the
AUTONOMOUS_REWEAVE log. No completion flag, gate, criterion or route changed.

3b. CROSS-PLATFORM DEFECT DETECTED BY CI AND REPAIRED
======================================================================

The first push of this knot (commit e79ac1d5) passed the local full suite on
Windows (276/276 suites, 2126/2126 tests, also in --ci --runInBand) but FAILED
three Linux CI jobs that all run the same Jest suite: Autonomous Builder
Validation (job validate-autonomous-builder), HooshyarOS Validation (job
validate) and HooshyarOS CI (job verify -> "Full Jest suite"). The successful
pre-change runs at 02a13510 had durations comparable to the failing ones
(HooshyarOS Validation 1.8 min success vs 1.9 min failure), so this was a
normal deterministic test failure, not an infrastructure crash.

Root cause (proven by reading the code against Linux semantics): the
reverse-dependency scanner lower-cased the absolute path before probing the
filesystem (`resolveSpecifier`). On a case-insensitive host (Windows) the
lower-cased probe still resolves; on a case-sensitive host (Linux) it does not,
because the mkdtemp/session path contains upper-case characters. The
reverse-import probe therefore never found the importer and the blast-radius
assertion failed. The Windows local run masked a real cross-platform defect.

Repair (canonical owner, minimal):
  - resolveSpecifier now probes the real, case-preserving path and returns
    undefined when no file exists (no fabricated path).
  - the target comparison is performed case-insensitively at the CALL SITE
    (resolved.toLowerCase() vs the lower-cased target set), so probe and
    compare are separated correctly.
  - The focused test now builds the fixture under a deterministic mixed-case
    checkout directory ("CaseSensitiveRepo") so this class is guarded on every
    host, not only when the temp-name happens to contain upper-case characters.
  - The analyzer file's spurious UTF-8 BOM was removed.

Post-repair local verification: focused test 10/10 PASS; changed-file typecheck
0 errors.

CI confirmation at the repair commit `c9904dcb93026c2156687d12c8326e6ff9159d5e`: the three Linux jobs
that failed at `e79ac1d5` are green:
